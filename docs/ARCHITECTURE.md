# 設計と技術的な判断

## 目的と構成

ファイル検索・容量確認・ファイル比較を同じ画面構成で操作でき、並列処理と逐次処理を切り替えて確認できるデスクトップツールを作ることを目的としています。

GUIはegui/eframeで実装し、`Request` をワーカーへ渡します。ワーカーは `engine::run` の結果を `std::sync::mpsc` チャネルで返します。エンジンはGUIに依存しないため、テストから実ファイルを直接検証できます。

進捗と中止フラグは `Arc<Progress>` のアトミック変数を共有します。これらは結果データの受け渡しを担わないため `Relaxed` 順序を使い、完成した結果はチャネルで同期します。処理中のGUIは約100ms間隔で再描画を要求します。

## 探索と並列化

1. 指定パスを実体パスに正規化し、無効な入力を検証します。
2. 重複ルートと親ルートに含まれる子ルートを除外します。
3. 探索待ちディレクトリのバッチを順番に、またはRayonの専用プールで処理します。
4. 読込結果を集約し、次のバッチに進みます。
5. 機能に応じてグループ化・並び替えを行い、`Report` を返します。

専用プールによってスレッド数を指定できます。探索はフォルダ単位なので、1フォルダに大量のファイルがある場合、その列挙自体は逐次処理です。HDDやネットワークストレージでは並列化により遅くなる可能性もあります。

シンボリックリンク、Windowsのジャンクションとその他の再解析ポイントは配下の探索から除外し、循環と意図しない探索範囲の拡大を避けます。ハードリンクの異なるパスは別項目として数えます。

## SHA-256比較

ファイルごとに1 MiBのバッファを確保し、読み込んだブロックを `sha2` に渡します。メモリ使用量はファイルサイズではなく、同時に処理するファイル数に比例します。単一ファイルのハッシュ計算を複数スレッドへ分割する方式ではありません。

読込前後のサイズ・更新日時と実際の読込バイト数を比較し、変更を検出した場合はエラーにします。ただし排他ロックやスナップショットではなく、あらゆる同時変更の検出を保証するものではありません。エラーまたは中止があれば全体一致を判定しません。

## 結果・中止・エラー

エラーは総件数と最大200件の詳細を保持し、残りの対象の処理を続けます。中止は各エントリ／読込ブロックの間で確認します。OSの入出力待ち、結果のグループ化・ソートを途中で強制終了する設計ではありません。

結果一覧は仮想スクロールを使い、可視行だけウィジェットを生成します。結果データは全件保持するため、数百万件規模でのメモリ使用量は今後の検証対象です。再ソートとCSV保存はGUIスレッドで実行しており、大量の結果ではその間応答が遅くなる可能性があります。

CSVには完了／一部エラー／中止の状態を記録します。ファイル名・パスはCSVの引用処理を行い、数式として解釈される先頭文字に対してアポストロフィを付加します。

## 検証と今後の改善

一時ディレクトリに実ファイルを作り、期待する件数・バイト数・既知のハッシュを検証します。並列と逐次では時間以外の結果が一致することを確認します。中止のテストは開始前だけでなく、ハッシュの読込が始まった後にも要求を送ります。

CIではRust 1.92.0とstableのWindows環境でfmt・Clippy・テスト・リリースビルドを実行します。配布時には静的CRTを使うWindowsターゲットでリリースモードのテストも実行します。GUIの見た目、ダイアログ、実機ストレージの特性は手動確認の対象です。

今後の検討対象は、ストレージ別のベンチマークとメモリ計測、大量の結果に対するソート・CSV保存のバックグラウンド化、検索条件や設定保存の拡張、他OSでのGUI検証です。これらは未実装です。
